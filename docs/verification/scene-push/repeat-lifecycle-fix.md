# 首条之后循环被触发条件误停的修复

2026-10-22，用户日志显示：13101 首次发布成功、循环开关开启且次数为 8，但第一轮重复前出现“原触发条件已取消”，随后结束。这条路径没有调用第二次 notify。

## 已复现的代码缺陷

同一次连接可能先更新 plugged、后更新 charging，也可能相反。旧实现两次均重建 session；第二次又被 5 分钟防抖抑制，未生成新候选，导致已经保存的第一次 reference 被判不匹配。

新增两条回归用例在修复前均失败：接电→开始充电，以及开始充电→补全接电。修复后同一连接的状态补全保留 session 和原始起始时间，实际断开/新的充电周期仍按原规则处理。

## 展示周期与触发条件解耦

原触发条件继续用于候选、排队、出队和首条发布前校验。首条成功后，循环更新的是同一条已展示通知，不再次核验原始电池、网络、文件快照。源事件取消只撤销尚未展示的候选，不取消正在播放的一轮。

仍然检查循环/场景开关、次数、前后台、通知权限、队列展示位、系统中通知是否存在及轮次 token；划除、点击自动取消、回前台、权限撤销、开关关闭和服务结束仍会停止，不复活被删除的通知。旧推送循环与每日额度未改动。

## 验证

- local 应用/测试编译、notification Lint 与 `git diff --check` 通过。
- notification 单元测试 138 项通过，包含两条先失败后通过的充电分阶段上报回归。
- API 37 场景与每日额度设备测试 15 项通过。队列测试在 A 首条成功后主动使其原触发条件变为 false，并发送候选取消，A 仍完成首次重复和展示窗口；尚未展示的 C 不满足条件时仍被跳过。
- 最新 local APK 上旧通知布局、提醒策略和来源埋点回归 9 项通过。
- 实际 Logcat 已出现充电开始与网络变化的“重复提交成功，额外循环序号=1”，不再出现旧循环阶段的“原触发条件已取消，停止重复发布”。这验证的是重复发布路径，系统最终悬浮表现仍受 Android/OEM 通知策略控制。
