# 新场景触发事件 FIFO 队列

2026-10-22。按用户澄清，排队的是**尚未展示的触发条件/事件**，不是已创建或已展示的通知。

## 流程

1. 原事件来源生成有界元数据，原有延迟和该场景独立间隔继续生效。
2. 满足展示时间条件后等待 `ScenePresentationQueue` 的 FIFO 展示位。每场景最多一个待处理候选，不生成 Notification/RemoteViews、不选定文案、不计次数。
3. 取得展示位后读取最新配置、频控、事实和文案，再首次 notify。队列不按等待时长设置过期；若权限撤销、开关关闭、文件已删除或重新插电取消了充电结束事件，仍按原有规则不发。
4. 当前通知完整循环后交棒，最后一次发布仍保留 4 秒窗口。例如循环次数 1：0 秒首次发布，4 秒重复，8 秒下一事件才能首次发布。关闭循环时首条占用 4 秒。划除可提前结束当前轮并交棒。
5. 循环完成后通知可以留在通知栏；它不会重新进入队列。回前台或服务结束清空待处理事件，停止本次服务会话的循环，不做持久恢复。

独立通知 ID、各场景间隔、原开关/循环次数、文案轮播和点击链路保留。没有优先级排序或每日总上限。旧推送不入队、不被新队列阻塞/取消。

## 验证

- local 应用与测试 APK 编译、notification Lint、`git diff --check` 通过。
- notification 单元测试共 134 项通过。新增 11 项队列/播放测试覆盖 FIFO、同场景候选合并、旧展示位不能释放新持有者、等待中及刚晋升时取消、回前台清空、关闭服务、整轮及末尾窗口、排队不计数、出队重新选择文案、条件取消、发布失败继续下一条、远程延长间隔不阻塞其他场景。
- API 37 设备测试 15 项通过。真实系统通知中验证：A 首条及重复时 B/C/D 均未发布；满 8 秒 B 才首次发布；收到 B 的划除回调后跳过不再满足条件的 C，D 首次发布；只有 A/B/D 产生 Show 和历史计数，旧通知仍保留。
- 最新 local APK 上的旧通知布局、提醒策略、来源埋点回归 9 项通过。
- 本次不修改视觉布局，沿用之前的截图和动效验收；新增验证集中在真实系统发布顺序。没有向真实手机发合成通知、修改系统时间、构建 google 渠道或提交 Git。
